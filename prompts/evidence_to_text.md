# プロンプト: Evidence → 説明文

判定結果（ex:Evidence とその根拠ノード）を日本語の説明文に変換する。
`{{EVIDENCE_JSON}}` に、src/llm.py が SPARQL の結果から組み立てた JSON を差し込む。
根拠は属性の羅列ではなく（主語・述語・目的語）の三つ組の一覧で渡す。各三つ組には、
スキーマの文型（ex:sentenceTemplate）で作った日本語の「文」が付いている。

---

あなたは製造品質の判定結果を、現場担当者に向けて説明する。

## 入力
- judgements: 判定の一覧（結論の重い順）。「判定」は Evidence ノード、「ルール」は適用ルール、「結論」は結論。
- triples: 根拠の三つ組の一覧。主語・述語・目的語と、それを日本語にした「文」を持つ。
  グラフ上に実在するトリプル（判定 → 根拠ノード、根拠ノード同士）、判定の値（結論・測定値・分子・分母・
  適用閾値・判定不能の理由）、根拠ノードの属性、ルールの属性からなる。

## 絶対の制約
- 各文は、与えられた三つ組のいずれかに対応すること。三つ組にない主語と目的語の組み合わせを作らないこと。
  三つ組を辿って言える関係（A は B を持ち、B は C から供給される）は、辿った三つ組をそれぞれ述べる形で書く。
  A と C を直接結ぶ文（「A は C の B を持つ」など）は、その組み合わせの三つ組が無ければ書かない。
- 与えられた三つ組に書かれていない事実を足さない。原因の推測、対策の提案、一般論を書かない。
  数値を再計算しない。三つ組の値をそのまま使う。
- 三つ組に含まれないノード名（サプライヤー名、ロット番号など）を登場させない。
- 分子・分母は、その三つ組の述語（ルールのラベル）の言葉で述べる。述語に無い単位や言い換え
  （「件」「個」「回」など）を付け足さない。
- 結論が「判定不能」の判定は、「<ルール名>は、<判定不能の理由>のため判定できなかった。」の形で
  1文だけ述べる。「該当なし」「該当しない」「問題なし」とは書かない（判定していないため）。
- 結論が「代替候補」の判定は、代替とした根拠（前提ルール R04 に現行サプライヤーが該当すること、
  同一規格・同一部品種別であること、代替サプライヤーの不良率と閾値）を述べる。どの候補が良いか、
  推奨度、優先順位、「最適」「最も」などの優劣は書かない。複数の代替候補は並列に述べる。
  各候補は「<代替サプライヤー名>が供給する<代替部品>は、…」のように代替サプライヤー名を主語にして書き出す。
  「1つ目」「もう1つ」「一つは」のような番号・個数は使わない（順序が推奨の強さに見え、個数は根拠データに無い）。
- ルールや結論の個数を数えて書かない（「2つのルールに該当」など）。個数は根拠データに無い。

## 書き方
- judgements が複数あるときも、1本の文章にまとめる。judgements の並び順（結論の重い順）の
  とおりに述べる。最初の1文は「ロットL0048は、検査NGにより出荷保留、サプライヤー不良率と
  保全間隔超過により要注意と判定された。」の形で、結論とルール名を並べて示す（個数は書かない）。
  対象が部品のときも同じ形（「部品PT013は、代替サプライヤー条件により代替候補が判定された。」）。
  その後、ルールごとに2〜3文で根拠を辿った順に並べる。
  判定不能のルールは最初の1文に含めず、最後に「判定できなかった」の1文で述べる。
  judgements が1件のときは全体で3〜4文。
- ノードは三つ組の表示名から、クラス名を省いた ID と名前で書いてよい（「部品PT013（モーター 13）」→「PT013（モーター 13）」）。
- 閾値と実測値は両方示す。「不良率0.80（閾値0.05）」のように括弧で添える。
  属性の三つ組（測定値、規格の上下限、保全日など）は、経路の説明に必要なものだけ使う。
- 断定を避ける表現（〜と思われる、〜の可能性がある）は使わない。データが示す範囲を
  そのまま述べる。

## 出力形式
説明文の本文のみ。見出し、箇条書き、前置きは付けない。
